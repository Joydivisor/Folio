# V1.0.0 beta 输出体验调研与实施方案

调研日期：2026-11-04。应用基线：`1.0.0-beta.9` / `r4`，提交 `d2df2c6`。本文记录当时的源码检查、官方资料和离线探针结果。随后用户要求开工，当前实现与验收见 [beta.10 实施记录](beta10-plan.md)；下文“当前”均指调研时的 beta.9 基线。

发布约定：先在本地完成开发、回归和安装包验收，再上传。调研阶段不改下载站、远程发布记录和安装包版本；后续 beta.10 仅在本地构建。产品名称可以使用“V1.0.0 Beta”；内部升级版本继续采用递增的 `1.0.0-beta.N`。现有 `release-info.js` 不接受不带序号的 `1.0.0-beta`，不宜直接将 beta.9 改成这个字符串。

## 结论

Folio 应当把“是否需要图”“图用什么引擎画”“是否打开独立编辑区”拆成三个决定。默认让解释、公式、表格和图示在同一条回答中按阅读顺序出现；需要持续编辑的作品才进入 Canvas 工作区。当前最影响体验的是强制单一展示类型、正文与演示互斥、追问缺少图形状态，以及整段等待的生成链路。

现有 3D 是有真实空间运算的群论专用演示器：三个预置多面体、绕原点轴旋转、顶点置换验证。它适合现有教学任务，但缺少通用场景描述、网格、材质、曲面和多物体关系。

Anatomy 可以作为机械结构、仪器和机制解释的辅助绘图库及创作指导。优先采用它的 SVG 核心和受控交互，按需加载 WebGL；其 beta 3D 不宜承担整个应用的通用 3D。接入重点是生成协议、隔离运行、验证和持久化，不能只把 `SKILL.md` 拼到现有提示词里。

## 1. ChatGPT 的公开输出逻辑

### 能核实的行为

OpenAI 在 2024 年的 Canvas 发布说明中把它定位为写作、编码及反复修改的协作界面，支持自动触发、用户明确要求使用、直接编辑、选择局部内容、反馈和历史回退。官方当时说明，触发与局部修改行为经过模型训练：长文创作是正例，一般问答应减少触发。这是历史设计说明，不能当作当前所有模型和客户端的精确规则。[Canvas 发布说明](https://openai.com/index/introducing-canvas/)

当前 Visualizations 文档把判断依据写为可视化是否实质改善理解、比较或探索：关系与过程用图示，数值用图表，输入、时间、运动或空间关系会变化时用交互形式。模型可以自主选择，用户也可以明确要求。该文档还说明，追问可能生成替代版本，并不保证始终原位修改。[Visualizations](https://learn.chatgpt.com/docs/visualizations)

当前插件 UI 指南主张从内嵌展示开始，在任务需要更多空间时扩大界面；独立编辑区和复杂浏览才使用更大的展示方式。这是公开的 UI 设计指导，不是 ChatGPT 内部路由代码。[插件 UI 指南](https://developers.openai.com/plugins/build/chatgpt-ui)

文件预览又是另一条路径：生成文件可在聊天旁打开，HTML 可提供预览和源码切换，支持针对具体位置反馈。它不等同于每次产生一张图就启动 Canvas。[文件预览与修改](https://learn.chatgpt.com/docs/artifacts-viewer)

### 对 Folio 的落地规则

下面是基于公开行为和本项目需求提出的规则，不是声称取得了 OpenAI 内部提示词或触发阈值。公开资料不足以复刻全部内部判断；“超过若干字或若干行一定打开”也不应写成产品规则。可以对齐用户可观察的体验，并用固定任务集验收。

| 用户任务 | 默认输出 | 独立编辑区 |
| --- | --- | --- |
| 简短定义、问一个原因、要求一句话 | 聊天中的简洁正文和必要公式 | 不自动打开 |
| 比较两个概念 | 按信息量选择正文或内嵌表格 | 通常不需要 |
| 解释有分支或循环的流程 | 一段说明、内嵌流程图、必要补充 | 用户放大或编辑时打开 |
| 多步证明 | 可连续阅读的推导；播放作为可选辅助 | 形成持续编辑的笔记时打开 |
| 拖动参数能帮助理解的问题 | 内嵌交互实验，文字说明保留 | 空间不足或复杂编辑时打开 |
| 写一份笔记、报告、代码，或明确说“用 Canvas” | 创建有身份和版本的作品 | 打开 |
| 对已有作品说“为什么第二步成立” | 回答问题并定位第二步 | 保持作品内容，不自动改写 |
| “只改第二个节点，其余保留” | 更新指定作品的指定部分 | 保留作品、视角、其它节点和历史 |
| 明确只要文字、不要图 | 文字 | 尊重明确偏好 |

自然嵌入应当体现为：段落与图在同一阅读流中；图出现在需要它的说明附近；工具栏轻量；字号、留白、配色一致；图可展开，收起后仍在原位置。不能把每段正文重复成图卡，也不能用大卡片和播放控件包住每个简短答案。

## 2. 当前实现与具体差距

| 位置 | 已确认行为 | 影响 |
| --- | --- | --- |
| `public/reading-response.js:18` | 一份回答只选择一个顶层 `kind` | 无法自然组织“解释 → 流程图 → 公式 → 对照表”的混合回答 |
| `public/reading-intent.js:5` | 比较、证明、process 等关键词直接给出展示偏好 | 短答、术语解释和否定语句容易被误判 |
| `public/reading-response.js:44` | 首轮校验把偏好视作必须采用的展示类型 | 模型即使合理地回答简短正文，也可能被要求重写为演示 |
| `public/artifact-workspace.js:23` | `select(true)` 默认显示演示并隐藏解释 | 用户不能连续阅读正文和图示 |
| `public/display-view.js:5` | process 与 derivation 共用逐步播放器，每次显示一步 | process 不具备流程节点、判断分支与回路的数据结构 |
| `public/graph-schema.js:7` | 概念图最多 7 个节点、24 条边，节点只有四种语义角色 | 小型概念图可用，完整算法流程、时序、泳道缺少专门语义 |
| `public/app.js:378` | 概念图在回答完成后发起第二次模型请求 | 先出现正文，再重绘为图，过程容易割裂 |
| `public/reading-response.js:32` | `current_artifact` 只有 plan 与 answer，没有 visual 和 interaction | 图节点的手动修改和当前选中状态未进入追问上下文 |
| `public/app.js:380` | 关系图请求只带选段、当前问题、原文上下文和 object | 生成关系图的第二阶段也缺少当前图，难以可靠局部修改 |
| `public/artifact-workspace.js:12` | 展示时重建整个作品 DOM | 未形成稳定的块级更新和视图复用 |
| `server.mjs:44` | `stream:false`，输出上限固定为 4096 tokens | 等完整响应才能呈现；复杂作品受单轮长度限制 |
| `public/reading-response.js:36` | 读取回答上限 40000 字符、最多 8 段 | 不适合直接承担较长的文档型 Canvas |
| `public/workspace-store.js:22` | `visual` 一律按概念图校验 | 加入 SVG、3D 或 Anatomy 需要升级数据契约与备份验证 |

这不是所有现有实现都需要重做。来源核验、数学运算、对象不替换规则、作品版本、过期修改检查、相机状态保存和备份机制都可以继续使用。

### 本次离线探针

对当前函数直接调用，不经过模型、不消耗 API 额度：

| 输入或检查 | 实际结果 |
| --- | --- |
| 用一句话比较群和环 | preferred 为 comparison；首轮合法 explain 被校验拒绝 |
| 不要画图，比较群和环 | preferred 为 comparison；文字偏好没有进入硬约束 |
| 只用文字解释立方体的旋转 | preferred 为 explain，正确保留文字 |
| 简单解释为什么这个证明成立 | preferred 为 derivation；首轮 explain 被拒绝 |
| What is a process? | preferred 为 process；把术语问答转成过程演示要求 |
| Explain the word proof | preferred 为 derivation；把术语问答转成推导要求 |
| use canvas 写一份可编辑笔记 | preferred 为 null；当前路由没有 Canvas 这一展示维度 |
| 给当前概念图放入自定义节点标记后生成追问提示词 | 提示词不含节点标记；interaction 也未传入 |

| 比较版本 1.0.0-beta 与 1.0.0-beta.9 | 当前版本解析器拒绝前者 |

这些是本地规则与数据传递的结果，不代表对真实模型自然语言理解能力的测量。

## 3. 3D 目前的能力边界

当前主阅读链路在 `app.js:283` 和 `app.js:284` 调用 `mountGeometry`。`geometry-view.js:4` 固定了三个模型的顶点；`display-plan.js:7` 对模型类型作白名单校验。历史 `scene-view.js` 有四面体专用的绘面代码，但不能据此认为当前通用 geometry 路径具备材质或网格引擎。

| 维度 | 目前具备 | 目前缺少 |
| --- | --- | --- |
| 对象 | 立方体、正四面体、正八面体 | 自定义网格、球柱锥、曲面、分子、导入模型 |
| 空间数学 | 三维坐标、轴角旋转、刚体距离检查、对称位置与置换 | 通用变换栈、偏心旋转轴、组合层级、平移缩放和形变协议 |
| 观察 | 拖动与键盘转视角、滚轮缩放、复位 | 通用选取、切面、测量、任意视图和多物体联动 |
| 渲染 | Canvas 2D 投影，线段与顶点，顶点按深度排序 | 通用面片遮挡、深度缓冲、灯光、材质、纹理、透明处理 |
| 动作 | 调整角度、作用一次、保存实验状态 | 通用时间轴、运动约束、碰撞及物理求解 |
| 学科覆盖 | 适合群论旋转与顶点置换 | 不能把任意数学/物理/生物原文自动转成正确场景 |

三维运算是真实的；限制来自专用对象协议和渲染能力。增加更多模型名称只能扩大示例范围，要明显提高上限，需要场景结构、受控几何构件、渲染器和验证层一起升级。

建议保留两条输出路线：

1. **数学与科学 3D**：真实坐标、可验证变换、曲线/曲面、向量及网格等，逐项定义支持范围。显示层可以升级到通用 WebGL 方案，但渲染器本身不负责判断数学是否正确。
2. **结构与机制插图**：机械装置、部件关系、拆解、参数与运动联动，适合 Anatomy。几何检查通过只表示所检查的几何约束通过，不能代替物理规律或论文事实核验。

## 4. Anatomy 的接入判断

审查版本固定为 [`1482e8469b0a9e0d8cc18ea2740a01423d29ae80`](https://github.com/wheresryan22/anatomy/tree/1482e8469b0a9e0d8cc18ea2740a01423d29ae80)。本次阅读了 README、SKILL、MIT LICENSE、核心代码片段和 3D 指南；没有执行远程脚本或在本机测量它的帧率。

### 可复用的部分

| 层 | 内容 | 在 Folio 中的用途 |
| --- | --- | --- |
| 创作指导 | `SKILL.md` 和 references | 按任务选取：先建立真实模型，再决定结构、绘制和交互 |
| SVG 核心 | `iso-kit.mjs`、`lathe.mjs`、`tube.mjs`、`iso.css` | 体块、轴测投影、圆形零件、管线、明暗与部件结构 |
| 动态效果 | `gl.mjs` | 对确有解释作用的水、光等效果按需使用 |
| 局部 3D | `turn.mjs`、`turn-build.mjs`、`turn-audit.mjs` | 小范围刚体运动、铰链和旋转对象，作为实验性能力 |
| 验证 | audit、capture、drive、lines、turn-check | 开发和受隔离的构建阶段进行几何、交互与画面检查 |

上游支持独立 HTML/SVG 和 React 输出；Folio 可以选择普通 JavaScript 路径，不需要为了它改成 React。上游框架无关路径以 Node 内建模块为主，浏览器检查依赖 Chrome/Chromium；Folio 已有 Electron，但上游查找浏览器的脚本仍需适配，不能假设安装包中自动存在所需命令。[README](https://github.com/wheresryan22/anatomy/blob/1482e8469b0a9e0d8cc18ea2740a01423d29ae80/README.md)

按仓库文件大小相加，四个 SVG 核心文件及 LICENSE 为 106192 字节；整个 kit 目录为 704017 字节。这只是源码体积，不包括模板、审计工具、生成结果、适配层或打包开销。主要工作量在集成与生成质量。

仓库采用 MIT 许可，文本列明可以复制、修改、分发，并要求保留版权和许可声明。内嵌时固定审查版本，随安装包提供声明。[LICENSE](https://github.com/wheresryan22/anatomy/blob/1482e8469b0a9e0d8cc18ea2740a01423d29ae80/LICENSE)

### 不应直接照搬的部分

- 它强调实物机械隐喻，并要求大量精细部件。群定义、证明、小型流程图和数据图表不宜为此变成复杂机械装置。
- 它的核心价值偏向轴测 SVG；可选 3D 有真实空间运动，但整体仍是专门的图形体系。上游明确写了只支持凸部件、复杂形体需拆解、深度顺序问题需修正、移动管线存在限制。[3D 已知限制](https://github.com/wheresryan22/anatomy/blob/1482e8469b0a9e0d8cc18ea2740a01423d29ae80/references/3d.md#16-known-limits)
- 上游 3D 状态仍是 beta。作者报告复杂场景的性能明显下降，并说明完整轨道审计可能需要较长时间；这些不是 Folio 实测指标，不能直接写成产品性能承诺。[3D 性能](https://github.com/wheresryan22/anatomy/blob/1482e8469b0a9e0d8cc18ea2740a01423d29ae80/references/3d.md#15-performance)
- 技能假定宿主代理可以编写文件、运行构建、打开浏览器、查看截图并迭代。Folio 当前是单轮 JSON 请求加有限修复，没有这一创作循环。
- “工具本身不需要 API key”指库和构建工具；在 Folio 中自动创作新图仍需模型，继续使用用户配置的模型服务。

### 推荐集成方式

首版内嵌经过审查的绘图库、模板和交互组件。模型输出受验证的对象、部件、参数与动作描述，应用用可信代码渲染；数值读数和动画由同一个计算模型驱动。这样可以先支持机械结构、受控拆解、滑块和旋转示意，不要求用户安装 Codex 或 Claude Code。

更自由的生成式插图作为独立能力建设：需要有限轮次的生成、构建、检查、修复和超时回退，不能把生成的 JavaScript 直接交给 Electron 主进程、宿主页面或普通 Node 子进程执行。

用于显示生成 HTML 的容器应与主应用数据隔离：不暴露 `folioDesktop`、文件权限、密钥、宿主存储和任意网络；使用独立来源/隔离会话与受限消息协议；所有消息校验作品身份、类型和大小。纯 JSON/可信渲染路径可以先落地，任意代码执行路径必须有独立的运行隔离方案。Electron 主窗口的 `sandbox:true` 并不自动实现作品级权限隔离。

保存记录需要包含渲染器版本、结构数据、交互状态及静态回退图；网络断开后，已保存的作品仍可在本地打开。上游社区发布和外链上传功能不属于本次集成。

## 5. 建议的实现顺序

### 第一批：自然阅读与触发判断

1. 将任务意图、展示位置和渲染器拆开。显式“只要文字”、句数限制与“用 Canvas”先处理；语义判断决定图是否有帮助，关键词仅作提示。
2. 默认同时呈现正文和图。逐步推导提供完整可读列表，播放与聚焦步骤为附加操作。放大图示不触发重新生成。
3. 建立稳定块 ID 的回答结构，允许正文、公式、表格、图示、实验交错出现。由旧 plan/answer/visual 适配到新结构，保持旧笔记和备份可打开。
4. 区分“问已有作品的问题”与“修改作品”。将当前图、选中块、用户修改及必要交互状态送入修改请求；采用版本检查和局部变更。
5. 分阶段显示生成进度，逐个呈现已验证的内容块；取消和失败时保留上个有效作品。后续接入流式传输时，不直接渲染未完成 JSON 或可执行片段。

建议涉及：`reading-intent.js`、`reading-response.js`、`artifact-workspace.js`、`display-view.js`、`app.js`、`conversations.js`、`server.mjs`、`workspace-store.js` 以及对应样式和数据迁移。

### 第二批：真正的图示与 Canvas

增加专门的流程结构：开始/结束、动作、判断、带标签的分支和回路。已有 ELK 可继续负责布局，明确图类型和数据语义比更换画图库优先。大型图采用展开查看；小图直接嵌入。

Canvas 以独立作品身份组织编辑、选区、撤销和版本。复用当前历史机制，避免每句追问都创建替代作品。先覆盖笔记和图示，再根据实际需求扩展代码编辑；不在 beta 名义下承诺完整复刻所有 ChatGPT 产品能力。

### 第三批：Anatomy 与 3D 扩展

先建立 renderer 注册表与能力描述，模型只选择真实可用的能力。引入 Anatomy SVG 和少量经过验证的机制模板；对比解释质量、生成耗时、模型成本和窄屏表现。复杂 WebGL、局部 3D 和任意代码创作分批纳入。

数学 3D 单独扩充场景协议及验证。现有群论实验继续由确定性数学函数计算，不能被漂亮但不准确的插图替代。

### 第四批：本地安装包

在功能与兼容性验收通过后，确定递增 beta 版本，生成独立本地构建目录和安装器。先验证安装、覆盖升级、用户数据恢复、离线资源、许可声明和卸载行为，再进入上传环节。需要同时更新包内版本与安装器信息，避免覆盖已验证的 beta.9 产物。

## 6. 验收用例

| 用例 | 预期 |
| --- | --- |
| 一句话比较两个对象 | 一句话；不被强制改成表格或工作区 |
| 不要图、只用文字解释 | 无图示自动触发，无校验重试去强迫生成图 |
| 解释 process / proof 单词含义 | 普通问答 |
